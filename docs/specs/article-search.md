# 문서 검색 API 구현 명세

서버 이슈 [21](https://github.com/wntopia/gikipedia-server/issues/21)의 제목·본문 검색 API를 추가한다. 검색 대상은 MongoDB 읽기 뷰다. 본문은 위키 문법을 제거한 텍스트로 검색하고, 같은 텍스트에서 발췌와 강조 구간을 만든다.

상태: 로컬 구현과 검증 완료. 배포는 별도 작업이다. 기준일은 2026-10-12이며 기준 커밋은 `4f83b1e0293bd9363feae57f90587a3e670d7c71`이다. 사용자는 인터뷰 결정과 아래 기본값을 승인했다.

## 사용자 확정 사항

| 항목 | 결정 |
| --- | --- |
| 검색 저장소 | MongoDB의 최신 문서 읽기 뷰 |
| 최신성 | 비동기 반영 허용. 저장 직후 검색 반영은 보장하지 않음 |
| 본문 표현 | 위키 문법을 제거한 표시용 텍스트 |
| 본문 검색 | 표시용 텍스트를 파생 필드에 저장하고 그 필드를 검색 |
| 기존 데이터 | 보존 불필요. 데이터 이행, 호환 처리, 전용 백필 명령 제외 |
| 일치 규칙 | 입력 전체를 하나의 연속 문자열로 검색. 단어별 분리 없음 |
| 결과 순서 | 제목 정확히 일치 → 제목에 포함 → 본문에만 포함 |
| 페이지네이션 | `page/size`와 전체 건수 제공 |

기존 데이터 보존 불필요 결정이 앞선 백필 추가 결정을 대체한다. 새 데이터는 본문과 검색용 본문이 함께 갱신돼야 한다.

## 구현 전 기준 상태

| 항목 | 현재 상태와 근거 |
| --- | --- |
| 코드 상태 | 조사 시 로컬 `develop`과 원격 `develop`의 기준 커밋이 같았고 작업 트리는 깨끗했음 |
| 빌드 | Kotlin 2.3.21, Spring Boot 4.1.1, JVM 25, Mill 1.1.8. `build.mill` 기준 |
| 문서 API | 생성, ID 조회, 본문 수정, 이미지 교체. 검색 API 없음 |
| MongoDB 모델 | `documentId`, `title`, `content`, `articleUpdatedAt` 등 보유. 검색용 본문 없음 |
| 동기화 | MySQL 커밋 후 `ArticleUpdatedEventListener`가 `ArticleMongoSynchronizer` 호출 |
| 정합성 검사 | Mongo 문서가 없거나 리비전이 뒤처졌을 때 복구. 파생 필드 누락만으로는 복구하지 않음 |
| 조회 경로 설정 | `article.read.source`는 현재 ID 조회의 MySQL 또는 Redis→Mongo 경로를 선택 |
| 인덱스 선언 | `ArticleMongoEntity`에 `document_id` 유일 인덱스 선언. 운영 DB의 실제 인덱스는 미확인 |
| 프론트 | 기본 브랜치의 검색 화면은 mock 사용. `SnippetSegment[]` 렌더링 구현 보유 |
| 기준 테스트 | `./mill test` 성공. 22개 테스트 클래스, 95개 통과, 실패·오류·건너뜀 0. 명령 실행 약 22초 |
| 기준 포맷 | `./mill spotless --check` 성공 |
| 경고 | 기준 테스트에서 Scala Unsafe 사용과 Mockito 동적 agent 로딩 경고 발생 |
| 실제 DB 검증 | 기존 Mongo 테스트는 mock 기반. 로컬 Docker CLI는 있으나 데몬 연결 실패 |

이 테스트 결과는 기존 코드의 기준 결과다. 신규 검색 기능의 검증 결과가 아니다. 운영 문서 수, 문서 크기, 동기화 지연, 검색 성능, 커버리지는 측정하지 않았다.

## API 기본값

```http
GET /api/v1/articles?q=급식&page=0&size=20
```

`ArticleSearchController`에서 목록 경로를 제공한다. `GET /api/v1/articles/{articleId}`와 구분한다. 요청 DTO는 `@Valid @ModelAttribute`로 받고, 본문 없이 쿼리 파라미터로 호출한다.

| 항목 | 기본값 |
| --- | --- |
| 접근 | 로그인 없이 호출 |
| `q` | 필수. 원본 입력 최대 100 Unicode 코드포인트. 양끝 공백 제거 후 빈 값 거부. MongoDB 정규식에 저장할 수 없는 NUL 문자 거부 |
| 내부 공백 | 입력 내부 공백은 유지. 단어 분리, 공백 삭제, 와일드카드 해석 없음 |
| 대소문자 | ASCII 영문 A–Z 대소문자를 무시. 공통 리터럴 패턴으로 DB 검색·순위 판정·강조에 같은 비교 정책 적용. 그 외 문자는 그대로 비교 |
| 정규화 | 한글 초성 검색, 자모 조합 변환, 악센트 제거, 제목 정규화는 이번 범위에서 제외 |
| 특수문자 | `.`, `*`, `[`, `]`, `\\`, `$` 등도 문자 그대로 검색 |
| `page` | 0부터 시작하는 정수. 기본 0, 음수 및 표현 범위를 벗어난 값은 거부 |
| `size` | 기본 20. 1 이상 50 이하 |
| 동률 정렬 | 원본 수정 시각 내림차순 → 문서 ID 내림차순 |
| 일치 문서 없음 | `200`, `items: []`, `totalElements: 0`, `totalPages: 0` |
| 마지막 페이지 초과 | `200`, 빈 `items`, 요청한 페이지 번호와 계산한 전체 건수 유지 |
| 잘못된 입력 | `400`. DB 조회 전에 검증 |
| 검색 저장소 오류 | 알려진 Mongo 연결 실패·쿼리 제한 시간 초과는 `503`. 빈 성공 결과로 바꾸지 않음 |
| 동시 실행 한도 | 인스턴스별 기본 4개. 한도에 도달하면 DB 호출·대기 없이 공통 형식의 `503` 반환 |
| 저장소 전환 | 검색은 MongoDB 전용. `article.read.source`의 영향을 받지 않으며 MySQL로 자동 전환하지 않음 |

`page * size`는 `Long`으로 계산한다. 전체 건수와 페이지 수도 `Long`을 사용한다. 임의의 최대 페이지 번호는 추가하지 않는다. 깊은 페이지의 비용은 실행 시간 제한과 성능 측정으로 확인한다.

응답은 기존 SDK의 `{ status, code, message, data }` 래퍼를 사용한다. 아래는 `data`의 예시다. Controller 반환값의 자동 래핑을 유지하며 이중으로 감싸지 않는다. 실제 직렬화와 오류 래핑은 HTTP 테스트로 검증한다. SDK가 DTO 바인딩·검증 오류를 처리하지 않으므로 검색 컨트롤러의 전용 예외 처리에서 공통 형식의 400 응답을 반환한다.

```json
{
  "items": [
    {
      "id": 1,
      "title": "급식 안내",
      "snippet": [
        { "text": "학교 ", "highlight": false },
        { "text": "급식", "highlight": true },
        { "text": " 시간과 이용 방법을 안내합니다.", "highlight": false }
      ],
      "updatedAt": "2026-10-12T00:00:00Z"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

`id`는 MySQL 문서 ID인 `documentId`다. `updatedAt`은 MongoDB 동기화 시각이 아닌 `articleUpdatedAt`이다. 중복 제목도 ID가 다르면 별도 결과다. 제목과 본문이 모두 일치해도 같은 문서는 한 번만 반환한다.

## 본문 변환 규칙

현재 프론트 [편집 도움말](https://github.com/wntopia/frontend/blob/main/src/widgets/edit-guide/ui/EditGuide.tsx)에 명시된 문법은 `== 제목 ==`과 `[[문서명]]`이다. [파서 구현 이슈 10](https://github.com/wntopia/frontend/issues/10)은 열려 있다. 아래 규칙을 초기 계약으로 문서화하고, 프론트 파서와 차이가 생기면 조정한다.

`ArticleSearchTextConverter`를 순수 함수로 만든다. 원문 `content`를 보존하면서 검색·발췌용 문자열만 생성한다.

1. 한 줄 전체가 정확히 두 개의 `=`로 둘러싸인 유효한 제목이면 바깥 표식을 제거한다. 내용이 비어 있으면 원문을 유지한다.
2. 유효한 `[[문서명]]`은 내부 텍스트로 변환한다. 문서 존재 여부는 조회하지 않는다.
3. 닫히지 않은 표식, 중첩 링크, 비어 있는 링크, 별칭 구문은 해석하지 않고 원문으로 남긴다. 링크 내부의 `[`, `]`, `|`, 줄바꿈을 허용하지 않는다.
4. 나머지 문자는 그대로 남긴다. HTML이나 Markdown을 해석하거나 실행하지 않는다.
5. 변환 후 연속 공백·탭·개행은 공백 하나로 합치고 양끝 공백을 제거한다. 블록 경계에서 단어가 붙지 않게 한다.

| 원문 | 표시용 검색 본문 |
| --- | --- |
| `[[급식]] 안내` | `급식 안내` |
| `== 개요 ==` 다음 줄에 `학교 [[급식]] 안내` | `개요 학교 급식 안내` |
| `급식실 이용 안내` | `급식실 이용 안내` |
| `닫히지 않은 [[급식` | `닫히지 않은 [[급식` |
| `[[대상\|별칭]]` | 같은 원문 유지 |

검색어 `급식 안내`는 첫 번째 예시에 일치하고 `급식실 이용 안내`에는 일치하지 않는다. 입력 내부 공백은 그대로 비교하므로 `급식  안내`는 공백 하나인 `급식 안내`와 다르다. 지원 문법 표식은 제거되고, 알 수 없는 문법 표식은 남아서 검색 대상이 될 수 있다.

## 저장 모델과 동기화

`ArticleMongoEntity`에 `searchText: String`을 추가하고 Mongo 필드명을 `search_text`로 매핑한다. 이는 인덱스 자체가 아니라 표시용 본문의 저장 필드다. 새 데이터의 필수 값으로 취급한다. 구형 문서 호환용 기본값이나 원문 검색 대체 경로를 추가하지 않는다.

`ArticleMongoSynchronizer`가 전달받은 `content`에서 `searchText`를 계산한다. 신규 삽입의 `setOnInsert`와 기존 문서 갱신의 `set`에 모두 포함한다. 기존 문서에서는 `content`와 `search_text`를 같은 업데이트로 반영한다. 현재의 리비전 조건과 오래된 이벤트 차단을 유지한다.

문서 생성, PUT 수정, 공동편집 저장, 기존 정합성 복구는 이 동기화 경로를 공유한다. 변환 로직을 각 쓰기 서비스에 중복 추가하지 않는다. MySQL 원문, 히스토리, Redis 문서 응답에 검색용 본문을 추가하지 않는다.

검색 Service에는 JPA `@Transactional`을 붙이지 않는다. Mongo 조회만으로 MySQL 트랜잭션이 열리지 않게 한다. 검색 결과 캐시는 이번 범위에서 추가하지 않는다.

## 검색 쿼리와 정렬

`ArticleSearchRepository`를 별도 컴포넌트로 두고 `MongoTemplate` 집계를 사용한다. 기존 ID 조회 Repository와 검색 집계의 책임을 구분한다.

1. 검증한 검색어를 정규식 리터럴로 안전하게 이스케이프한다. 사용자 입력을 JSON 쿼리나 실행 표현식으로 조립하지 않는다.
2. `title` 또는 `search_text`에 입력 전체가 포함된 문서를 선택한다.
3. `$regexMatch`와 `$switch`로 제목 전체 일치에 0, 제목 부분 일치에 1, 나머지에 2를 부여한다. 정확히 일치는 문자열 전체를 검사해야 한다. 끝의 줄바꿈 때문에 부분 일치를 정확히 일치로 판정하지 않도록 테스트한다.
4. 순위 오름차순, `article_updated_at` 내림차순, `document_id` 내림차순으로 정렬한다.
5. DB에서 `skip`과 `limit`을 적용한다. 애플리케이션이 전체 결과를 가져와 정렬하거나 자르지 않는다.
6. 문서 ID, 제목, 검색용 본문, 원본 수정 시각만 반환한다. 원문과 이미지 등 불필요한 필드는 정렬 전 투영에서 제외한다.
7. 같은 검색 조건으로 전체 건수를 별도 계산한다. 목록·건수 조건 생성 코드를 공유한다. 건수 쿼리에는 페이지 제한을 적용하지 않는다.

`$regexMatch`는 정규식 일치 여부를 반환하고 기본적으로 collation을 따르지 않는다. 비교 정책을 옵션과 패턴에서 명시해야 한다. [MongoDB 문서](https://www.mongodb.com/docs/v7.0/reference/operator/aggregation/regexmatch/)

페이지 목록과 건수 조회는 하나의 스냅샷으로 묶지 않는다. 동시 수정이 있으면 같은 응답의 건수와 목록이 잠시 다를 수 있다. 페이지를 넘기는 동안 데이터가 바뀌면 중복·누락도 가능하다. ID 정렬은 동률의 순서를 고정하지만 이 현상까지 막지는 않는다. [MongoDB 페이지네이션 문서](https://www.mongodb.com/docs/manual/reference/method/cursor.skip/)

## 발췌와 강조

서버가 `SnippetSegmentResDto(text, highlight)` 배열을 만든다. 프론트의 현재 `SnippetSegment[]` 구조와 대응한다. 프론트가 일치 위치를 다시 계산할 필요가 없게 한다. `text`는 일반 문자열이고 HTML 태그로 강조하지 않는다.

- 본문에 일치가 있으면 첫 일치 위치를 포함하는 구간을 선택한다.
- 기본 발췌 길이는 160 코드포인트, 첫 일치 앞의 문맥은 최대 40 코드포인트다. 앞이나 끝에 붙은 일치도 검색어 전체를 포함해야 한다.
- 제목만 일치하면 본문 앞부분을 사용한다. 표시용 본문이 비면 빈 배열을 반환한다.
- 잘라낸 앞뒤에는 각각 `…`를 추가한다. 생략 기호는 강조하지 않고 160자 제한과 별도로 센다.
- UTF-16 surrogate pair를 자르지 않는다. 결합문자와 ZWJ 이모지는 grapheme 경계로 확장해 통째로 포함한다. 경계 확장분만큼 160 코드포인트를 넘을 수 있다.
- 발췌 안의 겹치지 않는 모든 일치를 왼쪽부터 강조한다. 원래 표기와 대소문자는 유지한다.
- 인접한 비강조 구간은 합친다. 빈 조각은 내보내지 않는다.

DB와 JVM의 정규식 엔진이 다르므로 한글, 영문 대소문자, 특수문자, Unicode 경계를 실제 Mongo 테스트와 변환 테스트에서 대조한다. 서버가 검색했다고 판정한 본문 일치에 강조 구간을 만들 수 없는 경우는 검증 실패로 취급한다.

## 성능과 오류 처리

현재 구성은 자체 운영 MongoDB 7이며 WiredTiger 캐시 설정은 0.5GB다. 데이터량과 검색 부하는 미확인이다. 표시용 필드를 추가해도 포함 검색과 계산한 우선순위 정렬이 자동으로 인덱스를 타는 것은 아니다. 대소문자를 무시하는 `$regex`에는 일반적인 대소문자 무시 인덱스의 효과를 기대할 수 없다. [MongoDB 정규식 문서](https://www.mongodb.com/docs/v7.0/reference/operator/query/regex/)

`ArticleSearchEnvironment`에 DB 명령별 실행 시간 제한을 둔다. 초기값은 2초다. 목록과 건수 조회에 각각 적용하고 제한 시간 초과는 `503`으로 반환한다. 이는 HTTP 응답 2초 보장이나 측정한 성능 목표가 아니다. 드라이버 연결 대기와 두 쿼리의 합산 시간도 존재한다. 밀리초로 변환한 설정값이 0 이하이면 시작 시 거부한다. 최소 제한은 1ms다.

저장소 예외 중 연결 오류·실행 시간 초과만 검색 불가 오류로 변환한다. 프로그래밍 오류까지 모두 `503`으로 숨기지 않는다. 오류 응답에 쿼리 원문이나 내부 예외 정보를 포함하지 않는다.

`article.search.max-concurrent-requests`로 인스턴스별 동시 검색 실행 수를 제한한다. 기본값은 4이며 0·음수는 시작 시 거부한다. 입력 검증 후 `Semaphore.tryAcquire()`로 허가를 얻는다. 한도에 도달하면 DB를 호출하거나 허가를 기다리지 않고 기존 공통 오류 본문의 `503`을 반환한다. 허가는 건수 조회·목록 조회·발췌 생성 전체에 유지하고 성공·예외 모두 `finally`에서 반환한다. 기존 ID 조회에는 적용하지 않는다. 일시 과부하의 `503` 사용은 [RFC 9110 §15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#name-503-service-unavailable)를 따른다.

이 제한은 리뷰에서 확인한 무제한 동시 실행을 차단한다. 기본값 4는 운영 용량을 검증한 수치가 아니다. 초당 요청 수나 사용자별 점유를 제한하지 않으며 여러 인스턴스의 합산 상한도 아니다. 같은 DB를 공유하는 인스턴스 수가 N이고 각 상한이 4라면 동시 검색 실행은 최대 4N개다. 운영 부하에 맞게 값을 조정해야 하며, 인스턴스 증설 시에는 공유 DB의 합산 예산과 외부 유입 제한을 별도로 정해야 한다. 전체 스캔 비용과 지속적인 부하를 제거하는 변경은 아니다.

일반 제목·본문 인덱스를 먼저 추가해서 성능 해결로 간주하지 않는다. 실제 MongoDB에서 실행 계획과 쿼리 시간을 측정한다. 짧은 검색어, 흔한 검색어, 결과 없음, 긴 본문, 뒤쪽 페이지를 포함한다. 목표 데이터량과 처리량이 없으므로 운영 성능 통과를 선언할 기준은 아직 없다. 측정 결과가 요구 부하를 감당하지 못하면 검색 인덱스 설계를 별도 검토한다.

3. 검색 Repository와 실제 Mongo 테스트를 추가한다. DB 정렬 후 페이지 제한을 검증한다.

5. 요청·응답 DTO, Controller, Swagger, 실행 시간 제한을 연결한다.
6. HTTP 테스트, 전체 회귀 테스트, 포맷, 빌드를 확인한다.
7. 실행 계획과 응답 시간을 측정하고 지원 가능한 조건과 남은 한계를 보고한다.

## 적용 조건과 작업 범위

기존 데이터 이행과 백필은 구현하지 않는다. 새 필드가 없는 기존 데이터를 그대로 사용하는 배포는 지원하지 않는다. 적용 환경은 새 스키마의 데이터로 구성해야 한다. 실제 초기화 대상과 시점은 배포 작업에서 정한다. 이번 구현에서는 실제 사용 데이터를 초기화하거나 삭제하지 않았다. 통합 테스트는 전용 컨테이너의 테스트 데이터만 초기화한다.

MySQL 스키마와 문서 히스토리 형식은 바꾸지 않는다. 미작성 문서 노출과 역링크 저장은 [서버 이슈 22](https://github.com/wntopia/gikipedia-server/issues/22), 제목 유일성과 정규화는 [서버 이슈 20](https://github.com/wntopia/gikipedia-server/issues/20)의 범위다.

프론트 코드 수정은 [프론트 이슈 21](https://github.com/wntopia/frontend/issues/21)의 별도 작업이다. 프론트는 ID 링크 생성, `updatedAt` 날짜 표시, 전체 건수 표시, URL의 `q/page` 연결을 추가해야 한다. 서버 API 완성만으로 프론트 연동 완료를 주장하지 않는다.

## 남은 검증 사항

- 요청·페이지 제한, 발췌 길이, 대소문자 정책, 오류 코드, 제한 시간은 승인된 기본값이다.
- MongoDB 7.0.43과 JVM 25에서 한글·ASCII 영문·특수문자·이모지 비교를 검증했다. Unicode 전체 문자의 모든 조합을 검증한 것은 아니다.
- 프론트 파서는 아직 미구현이다. 서버의 초기 표시용 문법 계약을 프론트 구현과 맞춰야 한다.
- 저장 직후 검색 반영, 반영 지연의 상한, 동시 수정 중 고정된 페이지 결과는 보장하지 않는다.
- MongoDB 장애 때 MySQL로 전환하는 검색 경로는 없다. ID 조회 경로 전환 설정과 독립적이다.
- 로컬 Docker 데몬 연결과 실제 Mongo 테스트를 확인했다. 운영 목표 데이터량·처리량과 배포 데이터 초기화 범위는 아직 정하지 않았다.

신규 검증은 본문 변환 20개, 발췌·강조 19개, 서비스 12개, 설정 2개, HTTP 17개, 실제 MongoDB 통합 14개로 총 84개다. 기존 95개도 모두 통과했다. 통합 테스트는 Docker Desktop의 MongoDB 7.0.43 컨테이너에서 실행했다. 드라이버가 전송한 건수·목록 명령에 각각 `maxTimeMS: 2000`이 포함됨을 검증했다. HTTP의 503 변환은 저장소 예외를 주입해 검증했다. 실제 운영 네트워크 장애 시험은 수행하지 않았다.

최초 검증에서 발견한 문제는 다음과 같이 해결했다.

- 통합 테스트 코드의 문법 오류와 줄 길이 위반을 수정했다.
- Mongo 명령 감시 테스트가 콜백 이후 유효하지 않은 버퍼를 읽고 있었다. 콜백 안에서 BSON 명령을 복사하도록 수정했다.
- 실제 Mongo 문서 읽기에서 기존 `BaseMongoEntity.id`의 불변 필드 때문에 ID 복원이 실패했다. protected setter를 추가했고, 실제 조회에서 ID와 문서 필드가 복원되는 것을 검증했다.
- SDK는 DTO 바인딩·검증 오류를 공통 오류 본문으로 처리하지 않았다. 400 본문 검증 11건으로 실패를 재현하고, 별도 검색 컨트롤러의 예외 처리로 보완했다. 기존 문서 컨트롤러는 변경하지 않았다.

기준 코드에서도 발생하던 Scala Unsafe·Mockito 동적 agent 경고는 남아 있다. 코드 커버리지 수치는 측정하지 않았다. 운영 DB에 접근하거나 실제 사용 데이터를 삭제하지 않았다.

### 합성 성능 측정

환경은 로컬 macOS arm64, JVM 25, Docker Desktop, MongoDB 7.0.43이다. 문서 2,000개에 문서별 표시용 본문 1,805 코드포인트를 저장했다. 모든 문서는 같은 본문을 사용하고 제목은 `문서 <ID>`다. 각 조건을 한 번 준비 실행한 후, 순차적으로 5회 측정했다. 수치는 Repository의 전체 건수 조회와 페이지 목록 조회를 합친 시간이다. 발췌 생성, HTTP, 동시 부하, 운영 환경은 측정 대상이 아니다. 전체 회귀 테스트와 함께 실행했으므로 다른 테스트의 자원 사용도 영향을 줄 수 있다.

| `학` | 0 / 20 | 2,000 | 15.96ms | 16.15ms |

### 검색 유틸리티의 소유 범위

세 객체는 상태와 외부 I/O가 없는 유틸리티다. 그러나 순수 함수라는 사실만으로 전역 공용 패키지에 둘 근거가 되지는 않는다. 기존 `domain.article` 아래에 `util`을 두고 다음 규칙의 소유 범위를 유지한다.

| 객체 | 문서 도메인에 두는 이유 |
| --- | --- |
| `ArticleSearchTextConverter` | 지원하는 위키 문법과 `search_text` 변환 규칙을 구현한다. |
| `ArticleSearchSnippetBuilder` | 발췌 160 코드포인트·앞 문맥 40 코드포인트 정책을 구현하고 문서 응답 DTO를 만든다. |
| `ArticleSearchPattern` | 문서 검색의 ASCII 대소문자 일치 정책을 DB와 발췌에 동일하게 적용한다. 현재 사용 범위는 문서 검색뿐이다. |

저장소와 서비스가 `domain.article.util`을 참조한다. 저장소의 `service` 패키지 참조는 없다. `ArticleSearchPattern`의 기존 `global.util` 배치는 이 기준으로 재검토해 수정했다. 이 이동은 검색 동작을 변경하지 않는다. 서비스 인터페이스나 Spring 빈은 추가하지 않는다.

이동 후 Java 25를 명시해 전체 테스트 179개를 다시 실행했다. 28개 클래스에서 실패·오류·건너뜀은 0이다. `spotless --check`, `assembly`, `git diff --check`도 통과했다. 이동한 세 객체와 두 테스트의 본문은 패키지·import를 제외하면 이동 전과 동일하다.

### CI 포맷 실패

`dcfa4c5`의 CI는 테스트를 통과한 뒤 `ArticleSearchTextConverter`의 포맷 검사에서 실패했다. 로컬 기본 실행과 새 프로세스 실행은 통과했지만, `JAVA_HOME`에 Java 25를 명시한 새 프로세스에서는 같은 실패가 재현됐다. 해당 환경의 포매터가 여러 줄 `if` 조건을 조건별 한 줄로 분리했다. 이 변경 후 기본 환경과 Java 25 환경의 포맷 검사 모두 통과했다. 패키지 배치는 이 실패의 원인이 아니었다. 실행 환경에 따라 검사 결과가 달라진 포매터 내부 원인까지 규명한 것은 아니다.

### PR 리뷰 반영: 동시 검색 제한

[Copilot 리뷰 4244199654](https://github.com/wntopia/gikipedia-server/pull/32#discussion_r4244199654)는 익명 검색에 요청 실행 제한이 없어 MongoDB 자원이 고갈될 수 있다고 지적했다. VALID로 판정했다. 저장소는 요청마다 건수와 목록을 별도로 조회하고, 기존 `maxTime`은 동시 요청 수를 제한하지 않는다. 이 판단은 위 성능·오류 처리 명세와 [OWASP API4:2023](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)의 자원 소비 제한 원칙에 근거한다.

동시 검색 4개를 실행한 상태에서 추가 요청이 거부되지 않는 실패를 먼저 재현했다. 서비스의 검색 전체 구간에 인스턴스별 동시 실행 상한을 적용한 후 다음을 검증했다.

- 기본 상한 4와 설정 상한 1, 초과 요청의 즉시 거부와 DB 미호출, 반복 거부 후 상한 유지.
- 건수·목록 조회 중 제한 유지, 정상 종료와 각 조회의 연결·시간 초과·프로그래밍 예외 후 허가 반환.
- HTTP 공통 503 응답, 기존 ID 조회 허용, 검색 완료 후 다음 요청 허용, 0·음수 설정의 시작 실패.

추가 테스트는 11개다. 관련 42개와 전체 190개 테스트를 통과했다. 전체 28개 클래스에서 실패·오류·건너뜀은 0이다. Java 25를 명시한 `spotless --check`, `assembly`와 `git diff --check`도 통과했다. 운영 동시 부하 시험과 커버리지 측정은 수행하지 않았다.
